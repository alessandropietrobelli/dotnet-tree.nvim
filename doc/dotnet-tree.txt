1. INTRODUCTION                                 *dotnet-tree-introduction*

dotnet-tree renders a .NET solution the way the solution declares itself —
solution folders, projects, project references, package references — rather
than the way files sit on disk. It supports both the legacy `.sln` format and
the newer XML `.slnx` format, resolves package versions through Central
Package Management (`Directory.Packages.props`), and runs `dotnet` CLI actions
on the node under the cursor.

It is implemented as a custom source for neo-tree.nvim, not as a standalone
tree plugin. See |dotnet-tree-installation|.

==============================================================================
2. REQUIREMENTS                                 *dotnet-tree-requirements*

  - Neovim >= 0.9
  - neo-tree.nvim              https://github.com/nvim-neo-tree/neo-tree.nvim
  - the `dotnet` CLI on $PATH, for the build/run/test/watch/add actions only
  - optional, for `d` only: nvim-dap, and netcoredbg on $PATH or in mason

==============================================================================
3. INSTALLATION                                 *dotnet-tree-installation*

Installing the plugin is NOT sufficient. neo-tree resolves external sources by
calling `require()` on the source name, so "dotnet-tree" must appear in
neo-tree's `sources` list: >lua

    {
      "nvim-neo-tree/neo-tree.nvim",
      branch = "v3.x",
      lazy = false,
      dependencies = {
        "nvim-lua/plenary.nvim",
        "MunifTanjim/nui.nvim",
        "nvim-tree/nvim-web-devicons",
        "alessandropietrobelli/dotnet-tree.nvim",
      },
      opts = {
        sources = { "filesystem", "buffers", "git_status", "dotnet-tree" },
      },
    }
<
`lazy = false` is what neo-tree's own README recommends, and this source needs
it too. With neo-tree deferred behind a key mapping or a command, neither
plugin is on the 'runtimepath' yet, so |:checkhealth-dotnet-tree| reports that
no healthcheck exists, `:help dotnet-tree` fails with |E149|, and `:Neotree`
is not a command until the mapping has been pressed once. neo-tree does its
own lazy loading internally, so this costs nothing at startup.

`branch = "v3.x"` pins neo-tree to the major version this source is written
against.

4. USAGE                                               *dotnet-tree-usage*

                                                            *:Neotree-dotnet*
Open the tree: >
    :Neotree dotnet-tree reveal
<
The source looks for a solution under the current working directory. When a
repository contains more than one, press `s` to choose; the choice is
persisted per working directory in: >
    stdpath("state")/dotnet-tree/solutions.json
<
The tree refreshes automatically on |DiagnosticChanged| and after writing
`*.csproj`, `*.fsproj`, `*.vbproj`, `*.sln`, `*.slnx` or
`Directory.Packages.props`.

                                                        *dotnet-tree-quickfix*
BUILD OUTPUT

`b`, `B`, `c` and `C` send their diagnostics to the |quickfix| list, so a
failed build is a list you can jump through with |:cnext| rather than a
terminal buffer you have to read. The window opens only when the command
failed; a successful build is a single message. Errors MSBuild reports without
a line and column — a failed restore, a missing SDK, a bad import — are parsed
too, and they matter: a failed restore stops compilation, so nothing else —
no language server included — ever sees the compile errors underneath it.

MSBuild prints every diagnostic twice, and once per target framework on a
multi-targeted project. Those copies are collapsed into one entry per source
position.

`r`, `t` and `w` still open a terminal split, where their output is
interactive.

Other plugins' lists are left alone: a build replaces the list it created
itself and otherwise pushes a new one, so |:colder| still reaches your
previous |:grep|. If the build fails in a way the parser does not recognise,
the raw output goes to the list verbatim rather than being dropped.

                                                           *dotnet-tree-debug*
DEBUGGING

`d` debugs the project under the cursor. It resolves that project's own
output, builds it, and starts netcoredbg on the assembly the build produced:

  OutputType     decides whether there is an entry point to launch at all
  AssemblyName   decides what the produced file is called
  TargetFramework  decides which bin/Debug/<tfm>/ the assembly is in

Both dependencies are optional and are checked before anything else happens:

  nvim-dap       https://github.com/mfussenegger/nvim-dap
  netcoredbg     on $PATH, or installed with mason

Neither is required for the rest of the plugin, and their absence is a message
plus a |:checkhealth-dotnet-tree| entry, never an error inside the tree.

What `d` refuses, and why it says so instead of launching:

  a library                 no entry point; the runtime error you would get
                            instead says nothing about the real problem
  OutputType `$(Property)`  only MSBuild can resolve it, and guessing "Exe"
                            produces exactly that opaque error
  AssemblyName `$(...)`     the output path cannot be composed from it
  a failed build            the quickfix list stays on screen with the
                            compiler errors; no debugger is started

Building first is not politeness: without it the debugger attaches to whatever
the previous build left behind, and you end up stepping through code that is
not the code on screen.

A multi-targeted project asks which framework to debug. A project that
declares no `TargetFramework` of its own inherits it from the nearest
`Directory.Build.props`, as MSBuild does; when that file only chains to the
one above it with `$([MSBuild]::GetPathOfFileAbove(...))` — the usual shape of
a `src/Directory.Build.props` — the chain is followed. When the framework is
still unknown — written as `$(SomeProperty)`, which only MSBuild can expand —
it is resolved from what the build actually put under `bin/Debug/`.

A test project is a runnable assembly too -- xunit v3 test projects declare
`<OutputType>Exe</OutputType>` -- so `d` debugs one rather than refusing it,
and says so before launching: what you get is the whole test suite under the
debugger, and the dap session is named "(tests)". A project counts as a test
project when it declares `<IsTestProject>` or references
`Microsoft.NET.Test.Sdk`; an explicit `<IsTestProject>false</IsTestProject>`
wins over the package, as it does in MSBuild.

To debug a single test rather than the whole assembly, use neotest-dotnet:

  https://github.com/Issafalcon/neotest-dotnet

The `coreclr` adapter is registered with nvim-dap only if you have not
configured one yourself: an adapter you set up wins.

5. MAPPINGS                                         *dotnet-tree-mappings*

Defaults inside the dotnet-tree window. Press `?` for this list in Neovim.

  <cr>, o, 2-LeftMouse   open node
  <space>                toggle node
  R                      refresh tree
  z                      close all nodes
  Z                      expand all nodes
  ?                      show help
  s                      select solution
  e                      edit the project's .csproj
  a                      add package or project reference
  n                      new file from template
  b                      build project        -> quickfix
  B                      build solution       -> quickfix
  c                      clean project        -> quickfix
  C                      clean solution       -> quickfix
  r                      run project          -> terminal
  d                      debug project        -> nvim-dap
  t                      test project         -> terminal
  w                      watch (run / test / build)  -> terminal

See |dotnet-tree-quickfix| for what the build actions do with their output,
and |dotnet-tree-debug| for `d`.

==============================================================================
6. CONFIGURATION                               *dotnet-tree-configuration*

Configure it as a neo-tree source. The table is merged over
`require("dotnet-tree").default_config`: >lua

    opts = {
      sources = { "filesystem", "dotnet-tree" },
      ["dotnet-tree"] = {
        window = {
          position = "left",
          width = 40,
          mappings = {
            ["<2-LeftMouse>"] = "noop",
          },
        },
      },
    }
<
==============================================================================
7. HEALTH                                             *dotnet-tree-health*

                                                    *:checkhealth-dotnet-tree*
>
    :checkhealth dotnet-tree
<
Verifies the Neovim version, that neo-tree is installed, that "dotnet-tree" is
registered in neo-tree's sources, that `dotnet` is executable, and which
solutions are discoverable from the current working directory.

It also reports whether debugging is available — nvim-dap installed and
netcoredbg found — as a warning rather than an error: only `d` needs them.
See |dotnet-tree-debug|.

8. TROUBLESHOOTING                           *dotnet-tree-troubleshooting*

"Invalid argument: dotnet-tree"
    Raised by neo-tree's command parser. "dotnet-tree" is missing from
    neo-tree's `sources`. See |dotnet-tree-installation|.

'No healthcheck found for "dotnet-tree" plugin', "E149: No help for
dotnet-tree", or ":Neotree" is not an editor command
    neo-tree is being lazy-loaded, so neither plugin is on the 'runtimepath'
    yet. Set `lazy = false` on the neo-tree spec, as shown in
    |dotnet-tree-installation|.

"[dotnet-tree] no .sln/.slnx found under <path>"
    No solution below the current working directory. Start Neovim at the
    repository root, or press `s` to select one explicitly.
