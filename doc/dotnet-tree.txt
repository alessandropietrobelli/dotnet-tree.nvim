1. INTRODUCTION                                 *dotnet-tree-introduction*

dotnet-tree renders a .NET solution the way the solution declares itself —
solution folders, projects, project references, package references — rather
than the way files sit on disk. It supports both the legacy `.sln` format and
the newer XML `.slnx` format, resolves package versions through Central
Package Management (`Directory.Packages.props`), and runs `dotnet` CLI actions
on the node under the cursor.

A package node shows the version the build uses. `ⓒ` marks a version from
the `Directory.Packages.props` nearest to the project (and the file it
imports with `GetPathOfFileAbove`); `override` marks a version the project
pins with `VersionOverride`.

It is implemented as a custom source for neo-tree.nvim, not as a standalone
tree plugin. See |dotnet-tree-installation|.

==============================================================================
2. REQUIREMENTS                                 *dotnet-tree-requirements*

  - Neovim >= 0.9
  - neo-tree.nvim              https://github.com/nvim-neo-tree/neo-tree.nvim
  - the `dotnet` CLI on $PATH, for the build/run/test/watch/add actions only
  - optional, for `d` only: nvim-dap, and netcoredbg on $PATH or in mason

3. INSTALLATION                                 *dotnet-tree-installation*

Installing the plugin is NOT sufficient. neo-tree resolves external sources by
calling `require()` on the source name, so "dotnet-tree" must appear in
neo-tree's `sources` list: >lua

    {
      "nvim-neo-tree/neo-tree.nvim",
      branch = "v3.x",
      lazy = false,
      dependencies = {
        "nvim-lua/plenary.nvim",
        "MunifTanjim/nui.nvim",
        "nvim-tree/nvim-web-devicons",
        "alessandropietrobelli/dotnet-tree.nvim",
      },
      opts = {
        sources = { "filesystem", "buffers", "git_status", "dotnet-tree" },
      },
    }
<
`lazy = false` is what neo-tree's own README recommends, and this source needs
it too. With neo-tree deferred behind a key mapping or a command, neither
plugin is on the 'runtimepath' yet, so |:checkhealth-dotnet-tree| reports that
no healthcheck exists, `:help dotnet-tree` fails with |E149|, and `:Neotree`
is not a command until the mapping has been pressed once. neo-tree does its
own lazy loading internally, so this costs nothing at startup.

`branch = "v3.x"` pins neo-tree to the major version this source is written
against.

4. USAGE                                               *dotnet-tree-usage*

                                                            *:Neotree-dotnet*
Open the tree: >
    :Neotree dotnet-tree reveal
<
The source looks for a solution under the current working directory. When a
repository contains more than one, press `s` to choose; the choice is
persisted per working directory in: >
    stdpath("state")/dotnet-tree/solutions.json
<
The tree is rebuilt after writing `*.csproj`, `*.fsproj`, `*.vbproj`,
`*.sln`, `*.slnx` or `Directory.Packages.props`, and after writing a new
file inside a project. |DiagnosticChanged| only redraws it: the counts are
read again without rescanning the solution.

Git status is read in the background, after every rebuild, after writing a
file the tree shows, on |FocusGained|, on |TermClose| (lazygit and other
terminal clients) and after fugitive changes the repository. The tree is
rebuilt only when the status changed. If git fails, the markers already
shown stay and the error is reported once.

Files created, deleted or renamed outside Neovim appear on `R`.

                                                     *dotnet-tree-reveal*
`reveal` puts the cursor on the current file: the tree expands the solution,
any solution folders, the project and the folders above the file. A `.csproj`
lands on its project node. A file the tree does not show (outside every
project directory and not a solution item, or under `bin` and `obj`) leaves
the cursor where it is. A project nested inside another project's directory
has its files listed under both; the cursor goes to the copy under the
innermost project.

                                         *dotnet-tree-follow-current-file*
To do that on every buffer switch, without leaving the editor, enable
`follow_current_file`, the same option the filesystem source has: >lua

    ["dotnet-tree"] = {
      follow_current_file = {
        enabled = true,
        leave_dirs_open = false,
      },
    }
<
It acts only while the tree is on screen, and not when it is a float. With
`leave_dirs_open = false` the folders a previous reveal or follow opened are
closed again when the next file does not need them. A folder you open or
close yourself, with any mapping, is yours from then on and is left alone.

With the option enabled, neo-tree treats every `:Neotree dotnet-tree` as a
reveal of the current file, as it does for the filesystem source: opening
the tree also puts the cursor on the file you are editing. When that file is
outside the working directory (a decompiled source, a package under
`~/.nuget`), neo-tree asks first whether to change the working directory.
The question comes from neo-tree, and the answer does not move this tree,
which always shows the solution; answer no.

The tree finds the file by what it last rendered, so a file created since
then is followed after the next refresh (`R`, or saving the file or a
project file from Neovim).

                                                        *dotnet-tree-quickfix*
BUILD OUTPUT

`b`, `B`, `c` and `C` send their diagnostics to the |quickfix| list, so a
failed build is a list you can jump through with |:cnext| rather than a
terminal buffer you have to read. The window opens only when the command
failed; a successful build is a single message. Errors MSBuild reports without
a line and column — a failed restore, a missing SDK, a bad import — are parsed
too, and they matter: a failed restore stops compilation, so nothing else —
no language server included — ever sees the compile errors underneath it.

MSBuild prints every diagnostic twice, and once per target framework on a
multi-targeted project. Those copies are collapsed into one entry per source
position.

`r`, `t` and `w` still open a terminal split, where their output is
interactive. The terminal buffer is named after what it runs and on which
project — `dotnet-tree://run Api`, `dotnet-tree://watch test Api.Tests` — so
the split's |winbar| tells a run from a watch. A second terminal for the
same command, while the first is still open, gets a number: `run Api (2)`.

The terminal buffer is unlisted ('buflisted' off), so a bufferline does not
show it next to your files, where clicking it would open the terminal in the
editor window. Find it with |:ls!| or by its name.

Other plugins' lists are left alone: a build replaces the list it created
itself and otherwise pushes a new one, so |:colder| still reaches your
previous |:grep|. If the build fails in a way the parser does not recognise,
the raw output goes to the list verbatim rather than being dropped.

                                                           *dotnet-tree-debug*
DEBUGGING

`d` debugs the project under the cursor. It resolves that project's own
output, builds it, and starts netcoredbg on the assembly the build produced:

  OutputType     decides whether there is an entry point to launch at all,
                 and when the project declares none its SDK decides: the Web
                 and Worker SDKs build applications, which is why an ASP.NET
                 Core project never writes <OutputType>
  AssemblyName   decides what the produced file is called
  TargetFramework  decides which output a multi-targeted project means

The build is pinned to the `Debug` configuration, because that is what `d`
means: an optimised assembly is one netcoredbg warns about, and the warning is
that breakpoints will not be hit. `b` and `c` are not pinned — a project that
declares `Release` means it for the build.

Where the assembly is, though, is asked of MSBuild rather than composed:

>
    dotnet msbuild <project> -getProperty:TargetPath
<
`bin/Debug/<tfm>/<assembly>.dll` is only the default layout. A repository that
sets <ArtifactsPath> puts every project under one artifacts/ tree and has no
<project>/bin at all; <OutputPath>, <BaseOutputPath> and
<AppendTargetFrameworkToOutputPath> each move it somewhere else again. One
query answers for all of them, and it costs a fraction of the build that runs
just before it. `-getProperty` needs the .NET 8 SDK or newer; on an older SDK
the default layout is composed as it was before, which is no loss because the
artifacts layout is itself .NET 8 and later.

                                                  *dotnet-tree-launch-profile*
The launch profile is read too. `Properties/launchSettings.json` is what makes
`r` and `d` differ otherwise: `r` runs `dotnet run`, which reads it, and `d`
starts the assembly, which does not. On a `dotnet new webapi` that showed up as
the same project coming up in Development under one key and Production under
the other. Four things are taken from the profile:

  environmentVariables  the process environment, so ASPNETCORE_ENVIRONMENT is
                        Development and appsettings.Development.json is read
  applicationUrl        as ASPNETCORE_URLS, unless the profile sets that
                        variable itself
  commandLineArgs       the arguments, split the way a shell would
  workingDirectory      where the process starts, relative to the project

The profile is the one `dotnet run` would use with no `--launch-profile`: the
first `commandName: Project` profile in the file. Docker and IIS Express
profiles are skipped, because neither starts the assembly that was just built.
A project with no launchSettings.json, or one whose file cannot be parsed as
strict JSON, is launched exactly as it was before — the file is a source of
extra information, never a reason to refuse.

MSBuild is not evaluated here either: a value written as $(Property) is
dropped rather than exported verbatim.

Both dependencies are optional and are checked before anything else happens:

  nvim-dap       https://github.com/mfussenegger/nvim-dap
  netcoredbg     on $PATH, or installed with mason

Neither is required for the rest of the plugin, and their absence is a message
plus a |:checkhealth-dotnet-tree| entry, never an error inside the tree.

What `d` refuses, and why it says so instead of launching:

  a library                 no entry point; the runtime error you would get
                            instead says nothing about the real problem
  OutputType `$(Property)`  only MSBuild can resolve it, and guessing "Exe"
                            produces exactly that opaque error
  AssemblyName `$(...)`     the output path cannot be composed from it
  a Blazor WebAssembly app  MSBuild calls it an Exe, but it runs in the
                            browser; netcoredbg cannot start it
  a failed build            the quickfix list stays on screen with the
                            compiler errors; no debugger is started

Building first is not politeness: without it the debugger attaches to whatever
the previous build left behind, and you end up stepping through code that is
not the code on screen.

A multi-targeted project asks which framework to debug. A project that
declares no `TargetFramework` of its own inherits it from the nearest
`Directory.Build.props`, as MSBuild does; when that file only chains to the
one above it with `$([MSBuild]::GetPathOfFileAbove(...))` — the usual shape of
a `src/Directory.Build.props` — the chain is followed. When the framework is
still unknown — written as `$(SomeProperty)`, which only MSBuild can expand —
MSBuild is asked, and a single-targeted project needs no framework for that at
all: it names its one output. Only a multi-targeted project has no single
answer, and that is the case that asks.

A test project is a runnable assembly too -- xunit v3 test projects declare
`<OutputType>Exe</OutputType>` -- so `d` debugs one rather than refusing it,
and says so before launching: what you get is the whole test suite under the
debugger, and the dap session is named "(tests)". A project counts as a test
project when it declares `<IsTestProject>` or references
`Microsoft.NET.Test.Sdk`; an explicit `<IsTestProject>false</IsTestProject>`
wins over the package, as it does in MSBuild.

To debug a single test rather than the whole assembly, use neotest-dotnet:

  https://github.com/Issafalcon/neotest-dotnet

The `coreclr` adapter is registered with nvim-dap only if you have not
configured one yourself: an adapter you set up wins.

RUN, TEST AND WATCH                                     *dotnet-tree-run*

`r`, `t` and `w` open a terminal split that starts in the project's folder,
not in Neovim's working directory: the default ASP.NET Core host reads
appsettings.json from the directory it starts in. Neovim's own working
directory does not change.

                                                     *dotnet-tree-functions*
An Azure Functions app is one whose project file sets <AzureFunctionsVersion>
or whose folder has a host.json. It is started by the Functions host, so `r`
needs Azure Functions Core Tools (`func`) on $PATH and says so when it is
missing. What `r` runs depends on the SDK the project references, with its
version read the way the Packages node shows it (VersionOverride, then the
project, then Directory.Packages.props):

  Microsoft.Azure.Functions.Worker.Sdk 2.x   `dotnet run`, which starts
                                             `func start` itself
  Microsoft.Azure.Functions.Worker.Sdk 1.x   `func start`
  Microsoft.NET.Sdk.Functions (in-process)   `func start`

When local.settings.json sets AzureWebJobsStorage to
`UseDevelopmentStorage=true`, `r` checks that Azurite is listening on
127.0.0.1:10000 and warns when it is not. The app is started anyway: the
host runs without it, and reports its storage unhealthy.

NUGET.NVIM                                            *dotnet-tree-nuget*

With nuget.nvim installed, `a` hands packages over to it instead of asking for
a package name (https://github.com/alessandropietrobelli/nuget.nvim):

  - on a project's Packages node, it opens nuget.nvim's Browse tab, with that
    project already picked for the install;
  - on a package node, it opens nuget.nvim on that package: its versions per
    project, a newer one, advisories, deprecation.

Both use the solution selected in the tree. After nuget.nvim changes packages
the tree reads the projects again and reloads. Without nuget.nvim, `a` works
as before.

5. MAPPINGS                                         *dotnet-tree-mappings*

Defaults inside the dotnet-tree window. Press `?` for this list in Neovim.

  <cr>, o, 2-LeftMouse   open node
  <space>                toggle node
  R                      refresh tree
  z                      close all nodes
  Z                      expand all nodes
  ?                      show help
  s                      select solution
  e                      edit the project's .csproj
  a                      add package or project reference
                         (packages open nuget.nvim when it is installed:
                         |dotnet-tree-nuget|)
  n                      new file from template
  b                      build project        -> quickfix
  B                      build solution       -> quickfix
  c                      clean project        -> quickfix
  C                      clean solution       -> quickfix
  r                      run project          -> terminal
  d                      debug project        -> nvim-dap
  t                      test project         -> terminal
  w                      watch (run / test / build)  -> terminal

See |dotnet-tree-quickfix| for what the build actions do with their output,
and |dotnet-tree-debug| for `d`.

6. CONFIGURATION                               *dotnet-tree-configuration*

Configure it as a neo-tree source. The table is merged over
`require("dotnet-tree").default_config`: >lua

    opts = {
      sources = { "filesystem", "dotnet-tree" },
      ["dotnet-tree"] = {
        follow_current_file = {  -- |dotnet-tree-follow-current-file|
          enabled = false,
          leave_dirs_open = false,
        },
        window = {
          position = "left",
          width = 40,
          mappings = {
            ["<2-LeftMouse>"] = "noop",
          },
        },
      },
    }
<

7. HEALTH                                             *dotnet-tree-health*

                                                    *:checkhealth-dotnet-tree*
>
    :checkhealth dotnet-tree
<
Verifies the Neovim version, that neo-tree is installed, that "dotnet-tree" is
registered in neo-tree's sources, that `dotnet` is executable, and which
solutions are discoverable from the current working directory.

It also reports whether debugging is available — nvim-dap installed and
netcoredbg found — as a warning rather than an error: only `d` needs them.
See |dotnet-tree-debug|.

When a solution found there has an Azure Functions app, it reports whether
`func` is on $PATH and, if an app uses `UseDevelopmentStorage=true`, whether
Azurite is listening. See |dotnet-tree-functions|.

8. TROUBLESHOOTING                           *dotnet-tree-troubleshooting*

"Invalid argument: dotnet-tree"
    Raised by neo-tree's command parser. "dotnet-tree" is missing from
    neo-tree's `sources`. See |dotnet-tree-installation|.

'No healthcheck found for "dotnet-tree" plugin', "E149: No help for
dotnet-tree", or ":Neotree" is not an editor command
    neo-tree is being lazy-loaded, so neither plugin is on the 'runtimepath'
    yet. Set `lazy = false` on the neo-tree spec, as shown in
    |dotnet-tree-installation|.

"[dotnet-tree] no .sln/.slnx found under <path>"
    No solution below the current working directory. Start Neovim at the
    repository root, or press `s` to select one explicitly.
